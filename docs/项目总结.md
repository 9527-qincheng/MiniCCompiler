## 一、项目概述

### 1.1 做了什么

实现一个完整的 MiniC 编译器：输入 `.mc` 源文件，输出能在 Windows 上直接汇编链接并运行的
x86-64 汇编，同时提供六个阶段的中间产物用于核验与教学演示。

采用**挑战版文法**（LL(1) 预测分析，102 条产生式），相对基础版的差异：支持字符串、字符、布尔、
数组、函数（含递归与多实参）、`if`/`while` 控制流、`&&`/`||` 真短路求值、
int 与 float 的双向隐式转换。

## 二、技术架构

### 2.1 六阶段流水线

```
源文件 .mc
   │
   ├─① CLex          词法分析 ──→ .token.txt          （Token 流，带行列号）
   ├─② CParser       语法分析 ──→ .parse.txt / .ast.txt（LL(1) 分析轨迹 + AST）
   ├─③ SymbolTable   符号表   ──→ .sym.txt           （五节分表）
   ├─④ SemanticAnalyzer 语义  ──→ stderr 诊断        （带行列号，可多条）
   ├─⑤ IRGenerator   中间代码 ──→ .quad.txt          （四元式）
   └─⑥ CCodeGen      目标代码 ──→ .asm               （x86-64 / GNU as）
```

**门禁机制**（`src/main.cpp`）：`g_ErrorList` 非空即向 stderr 报错并 `return 1`；
目标代码阶段仍有门禁（前一段有错则不生成 `.asm`，避免拿残缺 AST 落下半截汇编）。
语义阶段**没有**门禁 —— 早期它被 `if (g_ErrorList.empty())` 整体挡住，导致「一批语法错
就把语义该报的问题全掩盖掉，看起来像一次只报一类问题」；2026-10-27 改为无条件执行，
并对语法已出错时产生的语义诊断追加 `(possibly caused by earlier lexical/syntax errors)` 后缀。


### 2.2 各模块设计要点

**① 词法 CLex（908 行 / 4 文件）**
终结符编码按设计文档编号（001~005 类型关键字、031~046 运算符、051 标识符、099 EOF）。
双字符运算符最长匹配优先（先试 `==` `!=` `<=` `>=` `&&` `||`，失败退回单字符）。
遇到非法字符报错后跳过继续扫描，一次编译列出全部词法错，而不是遇到第一个就退出。
字符与字符串支持转义（`\n` `\t` `\\` `\'` `\"`），未闭合字符串能单独报错。

**② 语法 CParser（2 700 行 / 6 文件）**
102 条产生式的 LL(1) 预测分析表驱动，**不是手写递归下降**。行为全部由 `g_Grammar` 数据层
驱动，文法一改行为自动跟着改；冲突在构造期（SELECT 集相交）就暴露，而不是运行时才发现解析不了。
额外提供 `--dump-parse` 输出完整的符号栈 / 剩余输入 / 动作轨迹，便于答辩讲解。
AST 为 18 类节点，前序打印且每节点带 `@行:列`。

**③ 符号表 SymbolTable（473 行 / 2 文件）**
五张分表（变量 / 常量 / 类型 / 过程 / 标号）+ 作用域栈 `m_varScopeStack`
（`vector<unordered_map<string, size_t>>`）。`RecVar` 只查当前作用域，内层同名变量合法遮蔽外层。
栈里存的是**扁平下标而非对象指针**——因为 `std::vector` 会 reallocate，存指针会失效。
`RecVarTbl` 重名时返回已存在的下标（而非新建表项），这是修正过的一个缺陷。

**④ 语义 SemanticAnalyzer（1 462 行 / 4 文件）**
遍历 18 类 AST 节点，做三件事：**登记**（写入符号表，`EnterScope`/`ExitScope` 与块结构严格成对）、
**校验**（未声明使用、重复定义、形参与体内变量同名、逻辑运算操作数必须 bool）、
**推导**（`DeduceBinOp` 统一出口推导表达式类型，必要时产出隐式转换告警 Q9）。

**⑤ 中间代码 IRGenerator**
两轮翻译：表达式递归求值产出临时变量 `_T1` `_T2`…；语句摊平成 `JZ`/`JMP`/`LABEL` 跳转。
两处关键实现：int 参与 float 运算时自动插 `ITOF`，回写时插 `FTOI`；`&&`/`||` 是**真短路**
（短路侧的操作数从不参与求值）。

**⑥ 目标代码 CCodeGen（1 121 行 / 2 文件）**
按 `QuadOp` switch 逐条翻译成 x86-64：`ITOF`→`cvtsi2ss`、`+`→`addss`、`FTOI`→`cvttss2si`、
`=`→`movl` 等。栈帧按局部变量数量分配，**16 字节栈对齐**（否则 `printf` 变参调用会崩）。
入口用 `global main` + `main:` 而非 `_start`，因为目标平台是 Windows MinGW，`_start` 无法链接。

路由上的两个实现细节：`Q_INDEX` 的读与写靠操作数位置区分（读 `(INDEX, 数组, 下标, t)`、
写 `(INDEX, 值, 下标, 数组)`），判定要看目的操作数是否是数组变量并配 `ElemWidth()`
（char→1，int/float→4）；形参表 `ParamEntry` 是扁平大表没有过程归属，用「名字 + 行号 + 列号」
三元组回连到变量表里的局部项。

### 2.3 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 分析算法 | LL(1) 预测分析表驱动 | 文法改动只改数据层；冲突在构造期暴露；可输出完整轨迹 |
| 汇编语法 | GNU as（AT&T） | 环境里有 `as` 与 `gcc`，能直接汇编链接验证；没装 nasm |
| 入口形态 | MinGW `main`（`global main` + `main:`） | 验收指南示例的 `_start` 是 Linux 入口，MinGW 下链接不了 |
| 翻译策略 | 朴素栈式，不做寄存器分配 | 正确性优先；每个变量与临时量固定 `%rbp` 栈槽 |
| 调用约定 | 自定义栈传参，`printf` 走 Win64 ABI | 实现简单可读，不受寄存器个数限制 |
| 中间产物 | 全部落盘为独立文件 | 出问题不用打断点猜；答辩时是最硬的证据 |
| 基线命名 | `*.expected.quad.txt` 而非 `*.quad.txt` | 后者会被任何人随手编一次 `test.mc` 就覆盖掉 |
| 测试口径 | 每层锁自己那一层的产物 | 端到端只比 stdout 会漏掉求值顺序、临时变量编号等结构性错误 |

## 三、关键成果

### 3.1 六段流水线全部打通

`tests/test.mc`（`int a; float b; a = b + 1;`）一次编译产出六个文件：

| 产物 | 大小 | 内容要点 |
|---|---:|---|
| `.token.txt` | 188 B | 14 个 Token，末行 `4:1 EOF <eof>` |
| `.parse.txt` | 10 194 B | 102 条产生式、66 步分析过程、结果「接受」 |
| `.ast.txt` | 152 B | `Program → Decl → Assign → BinOp`，每节点带 `@行:列` |
| `.sym.txt` | 208 B | 五节分表，`a : INT @line 1 scope 1` 等 |
| `.quad.txt` | 94 B | 4 条四元式，含 `ITOF`/`FTOI` |
| `.asm` | 1 216 B | 47 行，`.globl main`、栈帧 32 字节 |

四元式与汇编一一对应，可直接并排验证类型转换确实插对了：

```
(ITOF, 1, -, _T1)      →  cvtsi2ss
(+,    b, _T1, _T2)    →  addss
(FTOI, _T2, -, _T3)    →  cvttss2si
(=,    _T3, -, a)      →  movl
```

### 3.2 挑战版文法与 LL(1) 冲突消解

从**基础版文法**（int/float + 赋值 + 算术表达式）重做成挑战版，产出
`MiniC挑战版文法及其相关表格.xlsx`（214 905 B，15 个工作表）：
终结符 41 个（含 17 个挑战版新增）、非终结符 45 个、**LL(1) 预测分析表 45 × 41 = 1 845 格**
（工作表算上两行两列表头是 47 × 41），
另含 FIRST（85 行）/ FOLLOW（46 行）/ SELECT（93 行）/ 语义动作表 / 类型系统表 / 词法定义。

攻克的真问题：**`if`/`while` 的「否则部分」与 `else` 天然冲突**。
最终设计 `否则部分 → ε | else 语句`，**只剩 1 处 SELECT 冲突**
（`否则部分` × `else`，考试里这也是标准答案）。
`tests/run_grammar_selfcheck.ps1` 把它固化成 21 条断言，其中一条是：
`prediction table matches the SELECT sets cell by cell (only exception: 否则部分 x else)`。

配套还写了 `语法树工具/minic_ast.py`（29 700 B）：给任意 MiniC 源码就渲染出对应语法树 PNG
（Pillow + 微软雅黑），因为文档里的树形图是死的，评审要看自己的代码。
以及 `tools/parse2xlsx.py`（12 755 B）：把 `--dump-parse` 的轨迹转成 Excel 横向版式
（符号栈逐符号一格且右对齐、当前待匹配记号加粗标红、冻结窗格 `E6`、横向打印），
产物是 `docs/语法分析过程_ll1_411.xlsx`（82 步）与 `docs/语法分析过程_示例.xlsx`（173 步）。

### 3.3 修掉 12 处后端缺陷

全部是「只有真编译、真链接、真运行才会暴露」的问题，只看代码一个都发现不了。分 5 批：

**第一批（PR #17，`ef8298e`）——IR 四处**

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `&&`/`\|\|` 假短路 | `a && g()` 当 `a=false` 时 `g()` 里的 `print` 仍然输出 | 把操作符判断提前，先只求左操作数并发 `Q_JZ`/`Q_JNZ`，跳到中间标号后再求右操作数 |
| 实参不转类型 | `float half(float x); half(5)` 输出 `2.8026e-45`（把整数 5 当成了 float 的位模式） | 建 `m_ParamTypes` 表，`Q_PARA` 前按形参类型插 `ITOF`/`FTOI` |
| 返回值不转类型 | `float fi() { return 7; }` 调用方读到 0 | 新增 `m_curRetType`，翻译函数体前设为目标返回类型 |
| 赋值 int→float 缺 `ITOF` | `float f; f = 3;` 无转换 | 标量分支与数组写分支各补一条 |

**第二至第五批**

| 缺陷 | 现象 | 提交 |
|---|---|---|
| 嵌套调用实参错序 | `f(g(1), g(2))` 里外层 `PARA` 与内层 `CALL` 交错，实参被对调 | `339b6b4` |
| 空函数不产函数体 | `void f() {}` 只生成标号就结束 | `339b6b4` |
| 出错仍产 `.asm` | 前面阶段报错了还继续生成汇编，留下半截文件 | `339b6b4` |
| 重复 `main` 标号 | 用户自己也写 `int main()` 时与框架标号撞名 | `20a61f4` |
| 显式 return 被清零 | `return 42;` 之后又补了 `return 0`，结果恒为 0 | `e8a976d` |
| 裸 return 带残值 | `return;` 复用了上一个表达式的寄存器残留 | `e8a976d` |
| 无 return 返回垃圾 | int 函数不写 `return` 时返回栈上垃圾值 | `e8a976d` |
| 嵌套函数未拦截 | 函数里定义函数，文法允许但语义非法 | `96daa5f` |

**这一批的价值**：前端四段自己测全绿，接了目标代码之后才暴露这 12 个缺陷 ——
因为只有真把值算出来、真打印出来，才能发现「类型没转」「短路没生效」这类语义级错误。
**后端是前端的检验器**，这是本项目最值得讲的一条经验。

### 3.4 测试网从 5 套补齐到 11 套

| # | 套件 | 规模 | 比对对象 |
|---:|---|---|---|
| 1 | 词法回归 | 6 例 | `.token.txt` |
| 2 | 文法自检 | 21 项 | SELECT 集与预测表逐格 |
| 3 | 语法回归 | 49 例 | `.ast.txt` / `.err.txt` |
| 4 | 语法单元 | 17 输入 × 20 断言 | AST 不变量 |
| 5 | 符号表 | 8 组断言 | 作用域链 / 遮蔽 / 数组登记 |
| 6 | symtab 回归 | 1 例 | `.sym.txt` 基线 |
| 7 | **语义回归** | **18 例** | **诊断原文含行列号** |
| 8 | **四元式回归** | **17 例** | **`.quad.txt` 结构** |
| 9 | 目标代码 | 28 例 | 汇编→链接→运行→stdout |
| 10 | GUI 手册冒烟 | 55 条断言 | 渲染层 + 数据层 |
| 11 | GUI 示例冒烟 | 22 条断言 | 示例库数据层 + 15 条示例实跑 |

三个「为什么这么设计」：

- **词法回归不校验退出码**。词法用例是刻意的语法片段，parser 必然报错，用退出码判词法会产生
  误导；改为只比对 token 流，并对错误用例断言 stderr 必须有 `minic: error:`（防静默吞错）。
- **语义回归锁到「行列号 + 措辞」**。语义是四段前端里唯一没有独立回归的一段。位置错一位、
  措辞改一个字都要 FAIL，能防止「报了个错就算过」。
- **四元式回归单独立一套**。端到端只比 stdout 的话，表达式求值顺序、临时变量编号、标号编号、
  短路展开形态**全变了也照样输出对**，完全测不出来。

### 3.5 两组差分测试反查正确性

不靠肉眼读汇编，而是**拿另一个独立实现当基准**。做了两组，基准不同，互相补位：

**第一组：MiniC 版 vs gcc 编译的等价 C 版**（`build/_s2/`）
同一段逻辑写两份源码 —— `.mc` 走 minic，`.c` 走 gcc —— 逐行比对 stdout。
整数随机 **240 例** + 浮点随机 **240 例全部一致**；另覆盖边界场景：
`ack(3,3)=61`、深递归 20 000 层、100 个函数、50 层括号嵌套、5 000 元素局部数组（栈帧 20 032 字节）。

这一组踩到一个真实的语义陷阱，值得记下来：**C 参考版的浮点字面量必须加 `f` 后缀**，
否则 `3.1/12.8` 按 double 算成 `0.242188`，而 MiniC 按 float 算成 `0.242187` ——
**属语义差异不是缺陷**。差分测试的基准写错，会把正确实现判成错的。

**第二组：随机表达式树 vs Python 参考求值器**（`_tmpwork/diff2.py`、`diff3.py`）
随机生成表达式树（深度 4，覆盖 `+ - * /` 与括号、int 与 float 两套类型），
另写一份 Python 参考求值器（不共享编译器任何代码），编译→汇编→链接→运行，
stdout 与参考值逐字对照：

- int 有效用例 **207 例，0 不一致**（33 例因除零跳过）
- float 有效用例 **225 例，0 不一致**（15 例因除零跳过）
- 同一份源码两次编译，`.asm` 的 SHA256 完全一致（汇编确定性）

**为什么要两组**：第一组的基准是 gcc，能覆盖函数/递归/数组这类结构性问题；
第二组的基准是纯 Python 求值器，与被测实现没有任何共享代码，能覆盖运算符优先级与
类型转换这类语义细节。单靠任一组都会留盲区。

差分测试的实际产出：3.3 节里的 12 个后端缺陷，大部分是这两组测出来的 ——
实参错序、返回值语义、`main` 标号重复、IR 类型转换、短路求值，都属「单看代码几乎不可能发现」。

### 3.6 目标代码模块从零实现

`src/codegen/codegen.cpp` 从 **41 行 → 1 036 行**。起点是 `IRtoASM()` 只往 `AsmOutput` 里
push 7 行固定字符串：

```cpp
out.m_FileHeader.push_back("; MiniC target code (challenge) - TODO");
out.m_CodeSection.push_back("_start:");
out.m_CodeSection.push_back("; TODO: IR-to-ASM translation not implemented yet");
```

**关键认知**：这 7 行不随输入变化 —— 换个源文件，汇编一模一样。这是最典型的「假绿灯」：
能编译、能链接、能跑出 `.asm` 文件，产物里却没有真实内容。

现在的结构是匿名命名空间里的 `AsmEmitter`：
`Run()` 收集全局变量/数组到 `.bss`（`.align 8` + `.zero`）→ 逐函数生成栈帧
（局部变量按表下标升序，再临时量，`AlignUp(off, 16)`）→ 逐四元式 switch 翻译
（load → 运算 → store）→ 懒生成格式串 `.LCfmt_i` / `.LCfmt_f` / `.LCfmt_c`。

新增了 `BindSymTab()` 接口（属于「只新增、不破坏既有签名」的变更，已登记进 `docs/interface.md`
第 14 条），因为 `main.cpp` 只把顶层四元式传给 codegen，函数体的四元式在
`symtab.m_ProcInfoTbl[i].m_Codes` 里。

### 3.7 接口冻结与变更登记

`docs/interface.md` 记录了 **29 项对外接口**（24 项沿用设计文档第 6 章契约、5 项新增）
与 **22 条冲突/扩展记录**。5 项新增分别是：`CParser::GetTrace()`、`SymbolTable::RecArray()`
与 `SCOPE_BLOCK`、`SemanticAnalyzer` 的构造与 `Analyze()`、`IRGenerator::EmitIR()` 的
`LineInfo` 重载、`CCodeGen::BindSymTab()`。

其中最硬的一条是 **`Q_PARA` 的顺序约定**（第 17 条）：`Q_PARA` 必须紧邻在对应的 `Q_CALL`
之前且按实参顺序发出 —— 目标代码组直接依赖这个约定。不写下来，两个组各按自己的理解实现，
联调时必然对不上。

### 3.8 常量折叠：把设计文档里写了、代码里没做的那一项补上

设计文档挑战版特性表 C4 明写「常量折叠」，§9.2 的参考书对照表也列了
`TypeSysInfo + OpConstSemantic → 类型系统表 + 常量折叠`，但 `src/sema/ir.cpp` 里
**一行实现都没有**：`a = 4 / 2;` 会老老实实生成 `(/, 4, 2, _T1)`。

补上之后（`IRGenerator::FoldBinary` / `ConstFloat` / `ConstValueOf`，约 190 行）：

```
a = 1 + 2 * 3;      →  (=, 7, -, a)                    嵌套折叠，_T1/_T2 一起消失
a = 7 / 2;          →  (=, 3, -, a)                    C 语义向零截断，不是 3.5
a = 2 < 3;          →  (=, 1, -, a)                    关系运算也折成 bool 常量
a = 1.5 * 2.0;      →  (FTOI, 3, -, _T1) + (=, _T1, -, a)   折成浮点 3 后仍按 §8.1 插 FTOI
a = 1 + 2 * 3;  vs  a = 1; a + 2 * 3 → (+) 里的 2*3 折成常量 6，a + 6 保留
```

**三条边界是故意不折叠的**（注释里逐条写明理由）：

| 情形 | 为什么不折叠 |
|---|---|
| 除数为 0 | 编译期算出 `Inf` 会把「运行时除以零」变成「静默的错结果」，改变程序可见行为 |
| 整型结果越界 | `2147483647 + 1` 交给运行时按 x86 `addl` 自然回绕，与未折叠时的行为**逐位一致** |
| `&&` / `\|\|` | 短路有副作用语义（右侧可能不执行），必须保留 `Q_JZ`/`Q_JNZ` 分支 |

折叠点放在**类型转换之前**：`FoldBinary` 内部已按 §8.1 的 Promote 规则处理 int/float，
若先插 `ITOF` 再折叠，就会白生成一条转换四元式。

验证方式除了看四元式，还做了**变异测试**：把 `return GenIncDec(...)` 之外那行
`Operand folded = FoldBinary(...)` 改成恒返回空，`arith_int` 与 `const_fold` 两个用例
立刻 FAIL —— 证明这两条基线真的能拦住「折叠被删掉」。

### 3.9 让 `char` 真正参与运算：一处放宽，两层口径才对得上

`char` 从 v4.0 起就是一等类型（关键字 004、字面量 054、`TokenType::TOKEN_CHAR`），
但它在很长一段时间里**只能 `print`**：`c + 1` 报 `arithmetic operands must be numeric`、
`c == 'x'` 报 `relational operands must be numeric`。表面看是「挑战版没做这一项」，
查下来是**两层口径分裂**：

| 层 | 位置 | 对 `char` 的态度 |
|---|---|---|
| 语义 | `SemanticAnalyzer::IsNumeric`（`src/sema/semantic.cpp`） | 只认 `TOKEN_INT` / `TOKEN_FLOAT` → **拒绝** |
| 中间代码 | `IsIntType`（`src/sema/ir.cpp`） | 注释原文「char 在算术中按整数处理（C 语义）」→ **接受** |

也就是说 IR 侧早就准备好了，只是语义侧从来没放行——所以问题不在「没实现功能」，
而在「两个模块对同一件事的判断标准不一致，且没人对过」。

修法只有一行：`IsNumeric` 加上 `t == TokenType::TOKEN_CHAR`。`bool` 仍然排除，
布尔不参与算术是 §8.1 类型表定下的规则，这条没有松动。语义按 C 的整型提升走：
`c + 1` 得 `int`、`c == 'x'` 得 `bool`、`c + 1.5` 得 `float`。

目标代码层**零改动**：`char` 数组元素占 1 字节（写 `movb`、读 `movsbl` 符号扩展），
`char` 变量占 4 字节（`movl`），落到四元式层都是整数操作数，本来就不需要区分。

回归补了 4 个文件，其中 `tests/sema/err_bool_arith.mc` 是**反例**——锁住「`bool` 仍然被拒」，
防止以后有人顺手把 `bool` 也放宽。变异测试把 `TOKEN_CHAR` 改回不放行，
`char_arith` 的 quad 与 codegen 两个用例立刻 FAIL。

这件小事的价值不在功能本身，而在于它暴露的**判据问题**：一个类型「支持不支持」，
不能看词法里有没有这个 Token，也不能看文档里有没有这行字，
必须拿一段真实的程序编一次、跑一次，看它输出什么。§5.1「以代码为准」说的就是这个。

### 3.10 GUI 与语法手册

Electron 桌面端：7 类产物页签、暗亮双主题、内建语法手册（10 章 67 条，逐条实跑验证）、
15 条示例库（分 6 组）、运行输出页签（编译成功后自动 `gcc` 链接并跑起来，把 `print` 的
stdout 抓回界面）。

GUI 的编译链路与命令行**完全一致**：只是 `spawn minic.exe` 并读回产物，没有另写一套解析逻辑。
这一点让 GUI 的产物与命令行产物天然一致，也避免了「GUI 能跑但命令行跑不了」这类双轨问题。

## 四、遇到的困难与解决方式

### 4.1 接手时：「文档说的」和「代码是这样的」对不上

**问题**：交接文档写着「parser 约 80% 完成、AST 核心 TODO」，但实际 `parser.cpp` 早已完整。

**解决**：不采信文档，逐份读源码核实 —— 确认「以代码为准，文档滞后于代码」。
这个判断影响了后续所有工作方式：此后所有进度判断都基于实跑与源码，文档滞后就回写
（v3.1 → v4.0 → v4.0.1）。

**更严重的发现**：两个后端模块都有一份**完整的接口实现**，能编译、能链接、能跑出产物文件，
产物里却没有真实内容。这种状态比编译不过更危险，因为它不会被任何自动检查发现。

### 4.2 假绿灯：四轮提交都「能编译」但什么都没测

**问题**：语义模块组员提交了四轮代码（patch-1~4），每次都显示「编译通过」，实际是把文件放在了
仓库根目录而不是 `src/sema/`，根本没进编译列表 —— 等于什么都没测。

**解决**：
- 组长把 `SemanticAnalyzer` 按方案文档重写落到 `src/sema/`，并在 `src/main.cpp` 接线；
- 在 `build.bat list` 的输出里核对文件数，作为「有没有真进编译」的硬指标；
- 之后每加一个模块，都先确认它出现在 `build.bat list` 里，再谈测试。

**教训**：「能编译」不等于「被编译了」。假绿灯比红灯更危险，因为它不给任何提示。

### 4.3 构建脚本吞掉了退出码（既有代码的真实缺陷）

**问题**：`build.bat` 的 `:run` 与 `:test` 尾部原为两行 `endlocal` / `exit /b %RC%`。
`endlocal` 先执行会清空变量，下一行展开成裸 `exit /b` → **恒返回 0**。

**后果**：minic 的所有非零退出码对调用方完全不可见。测试全绿可能是假的，因为失败也返回 0。

**解决**：改为同行 `endlocal & exit /b %RC%`。

**这个 bug 的价值**：它直接催生了后面「变异测试」的做法 —— 不能只看测试输出绿不绿，
必须确认测试**会**变红。

### 4.4 语义模块四次失败：区分「能力问题」和「工具问题」

**问题**：语义组三次提交都不可用：patch-1 用废弃的 v3.1 AST API（45 个编译错误）、
patch-3 位置对了但没接线、patch-4 位置对了但**文件被网页编辑器毁掉**（每行被编号、中文乱码）。

**解决**：做对照实验 —— 只修 `main.cpp` 三处坏行 → 仍失败；**整份用正常文件替换 → 全绿**。
从而证明「不是能力问题，是工具问题」。于是方案从「退回重写」改成「整份文件替换 +
教他别用网页上传」，一次性解决。

**教训**：两类问题的处理方式完全不同。判错了方向，会把人推倒重来一遍，浪费的时间比修 bug 多。

### 4.5 中间代码是孤立历史，署名差点丢失

**问题**：张灏宇的 `feature/ir` 分支是**孤立历史**：`git rev-list --parents -n 1` 只有一个根提交
没有父提交，`git merge-base dev origin/feature/ir` 直接报 `fatal: no merge base`。

后果三条：GitHub **开不了 PR**（三点 diff 报错）；直接 `git merge` 会把两条无关历史并进来；
最要命的是这份 603 行代码**随时可能因为分支被清理而彻底丢失，作者署名一起消失**。

**解决**：
- 用 `git diff dev origin/feature/ir` 取出改动内容，基于 `dev` 新建 `feature/ir-rebased`
  （`c151654`）重新提交，保留原作者署名与提交信息，再走正常 PR 流程；
- 打 tag `archive/feature-ir-zhangyv522` 永久保留署名证据（原分支也留作备份不删）；
- 在 `docs/plans/README.md` 与 `docs/小组分工表.md` 里如实登记，并说明
  「`git log --author='zhangyv522'` 不加 `--all` 是 0 条，加 `--all` 才能看到 `c151654`」。

**教训**：「代码提交上来了」不等于「代码进仓库了」。判据是 `merge-base` 有没有结果，
不是 PR 页面能不能打开。

### 4.6 目标代码阶段一路踩出来的 8 个坑

这一段最适合写「困难与解决」，因为每个坑的现象和根因都不在同一层：

| # | 现象 | 根因 | 解法 |
|---:|---|---|---|
| 1 | `gcc x.asm` 报 `file format not recognized; treating as linker script` | gcc 不按后缀识别汇编语法 | 改名 `.s`，或显式加 `-x assembler` |
| 2 | 汇编报 `junk at end of line, first unrecognized character is '='` | **GNU as 在 Windows 上不认 `;` 作注释**（那是 nasm 的语法） | 全部注释前缀改成 `#` |
| 3 | 浮点打印出 `7.98984e-312` | **Windows 的 printf 不读 xmm 传参** | 除 `movss %xmm1` 外还要 `movq %xmm1, %rdx`，且 `movl $0, %eax` |
| 4 | `ld.exe: cannot open output file E:\...: No such file or directory` | MinGW 的 ld 不接受含中文的路径 | `Push-Location` 到仓库根后传相对路径 |
| 5 | `1.5` 编译成 `1.0`、`2.25` 成 `2.0` | `RecConst()` 只认 `TOKEN_NUM_FLOAT`，而语义阶段传的是 `NumType()` 返回的 `TOKEN_FLOAT` | 两个类型都判为浮点常量 |
| 6 | `ld.exe: cannot open output file build\minic.exe: Permission denied` | 上次运行残留的进程占着 exe | 先编到新文件名，`Stop-Process` 后 Move 覆盖 |
| 7 | 手算 17 个用例全对，但 `build.bat test` 一片红 | `Start-Process -PassThru` 在受限环境取不到 `ExitCode`（恒空） | 改用 `& exe ...; $LASTEXITCODE` |
| 8 | `mkdtemp` 建的临时目录既不可写也不可删 | 受限环境的目录权限 | 临时目录一律建在仓库 `build\` 下 |

**特别值得讲的一条**：坑 3（printf 浮点）和坑 5（浮点常量截断）是**两个独立缺陷叠在一起**——
如果只修一个，浮点输出依然是错的，但错法变了，很容易误判成「修过了还是不对」。
这类问题只能靠「打印中间产物」逐步定位，不能靠猜。

另一个陷阱：**选 float 的比较指令**要用 `ucomiss` 配 `setb / seta / setbe / setae`，
不能照抄整数那套 `setl / setg`。

### 4.7 中文路径下 minic.exe 文件 I/O 失效

**问题**：GUI 直接在工作区（路径含中文）里调用 `minic.exe` 时，产物文件写不出来。同类问题在
`ld.exe` 上也出现过（坑 4）。

**解决**：GUI 先把源码与 exe 复制到 `%TEMP%\minic-gui`（纯 ASCII 路径）再执行，
读回产物后再显示。这是 Windows 下 ANSI 文件 API 与 Unicode 路径的兼容问题，不是编译器缺陷。

### 4.8 测试脚本在受限环境里报「退出码为空」

**问题**：`run_parser_tests.ps1` 与 `run_symtab_tests.ps1` 用
`Start-Process -PassThru` 取 `.ExitCode`，在某些受限环境（如被沙箱限制的 shell）里恒为 `$null`，
导致 42 个用例全部 FAIL，报 `expected exit code 0, got`（got 后面是空的）。

**解决**：加直调回退 —— `.ExitCode` 为 `$null` 时改用 `& $Exe ...; $exitCode = $LASTEXITCODE`。
**这不是被测代码的缺陷，是测试脚本自身对环境的健壮性问题**，但当时如果不查清楚，
会误判成编译器有 42 个 bug。

### 4.9 LL(1) 带来的固有限制：顶层声明必须先于语句

**问题**：`int a; a = 1; int b;` 报语法错，而同样内容写在函数体里完全合法。

**根因**：产生式 `程序 → 声明部分 语句部分` 是**串联**不是交替。LL(1) 一旦看到
`FOLLOW(声明部分)`（即 `if`/`while`/`print`/`return`/`{`/`;`/标识符/EOF）就必须归约
`声明部分 → ε`，该符号永久出栈，之后再来 `int` 也回不去。

**为什么不改**：要支持「纯语句程序」（`print(1);` 单独成文件合法），就必须让
`FOLLOW(声明部分)` 包含全部语句起始符；而 LL(1) 见到 FOLLOW 即归约 ε →
「纯语句合法」与「声明可混排」在 LL(1) 下不可兼得。设计选了前者，这也符合
ANSI C（C89/C90 原本就要求块首声明，C99 才放宽）。

**处理**：在 `docs/MiniC语法支持清单.md` 里如实写明「顶层声明必须先于语句（函数体内不限）」，
并在答辩材料里主动解释成因，而不是等被问。

### 4.10 两次「看起来是 bug，其实不是」

这两件事的价值不在修了什么，而在**判断方法**：

**其一**：`while (a--) { b[a] = a; }` 报错，以为是写法问题。实际结论是 MiniC 挑战版文法
**根本没有 `++` / `--` 运算符**，`a--` 放在哪里都报错。证据：`src/lexer/token.h` 里只有
`TOKEN_PLUS`、`TOKEN_MINUS` 等单字符记号；`--dump-tokens` 会把 `a--` 拆成两个独立的 `MINUS`。

由此得到的自查技巧（比结论更有用）：跑 `minic.exe 文件.mc --dump-tokens`，
如果双字符符号被拆成两个单字符记号，基本可以判定文法没收录该运算符。

**其二**：截图里 `!=` 显示成了 `≠`，以为产物被污染。实际是**字体连字（ligature）**：
`gui/src/styles.css` 的字体栈里有 Cascadia Code 与 Sarasa Gothic SC，Chromium 默认开启 `calt`，
会把 `!=`→`≠`、`<=`→`≤`、`>=`→`≥`、`->`→`→`。`--dump-tokens` 的原始输出仍然是
`1:35 NE !=`。修法是给相关选择器加 `font-variant-ligatures: none`。

**教训**：「看起来错了」和「真的错了」之间要先做一次最小验证（这里是看 `--dump-tokens`
的原始字节）。直接改代码会把一个不存在的问题「修」出新问题。

## 五、经验总结

### 5.1 以代码为准，不以文档为准

接手时交接文档说 parser 只完成 80%，实际已完整；也出现过模块自称「已完成」但产物是空壳。
此后所有进度判断都基于实跑与源码，文档滞后就回写文档（v3.1 → v4.0 → v4.0.1）。

### 5.2 中间产物落盘，是最便宜的调试手段

把 Token、AST、符号表、四元式、汇编全部写成文件，出问题时不用打断点猜，
直接 `diff` 两份产物就能定位是哪一阶段变了。

答辩时这也是最好的证据：要说「类型转换插对了」，把 `.quad.txt` 和 `.asm` 并排一放即可，
不需要口头解释。

### 5.3 测试要锁住每一层的结构，而且必须验证它会失败

端到端只比 stdout 的话，求值顺序错了、临时变量编号乱了，输出照样是对的。
所以 11 套回归各自锁自己那一层的产物；语义甚至锁到「行列号 + 措辞」。

**「测试全绿」不等于「工程能用」，必须验证测试本身会失败。** 做法是变异测试：
篡改基线 → 必须 FAIL；删除基线 → 必须 FAIL；把错误用例改成合法输入 →
必须因「stderr 无 error」而 FAIL。三种变异都如期失败，才认定 runner 有效。

反例自证也是检验测试的方式：把 `err_undeclared` 的行号从 `6:5` 改成 `5:5`，必须立刻 FAIL；
把 `arith_int` 的 `(*, b, 3, _T1)` 改成 `(*, b, 4, _T1)`，必须立刻 FAIL。
改不动、改错了也不报错的测试，等于没写。

### 5.4 假绿灯比红灯更危险

红灯会告诉你哪里错了；假绿灯什么都不说，你以为一切正常。本项目踩到的假绿灯有四类：

1. **文件放错目录** → `build.bat list` 仍只收 `src/` 下的文件 → BUILD SUCCESS；
2. **构建脚本吞退出码**（`endlocal` bug）→ 失败也返回 0；
3. **产物是固定字符串** → 能跑出 `.asm`，但换个源文件内容一模一样；
4. **仓库无 CI** → `mergeable_state=clean` 只表示无文本冲突，不表示能编译。

对策：「能编译通过」至少要在三个层面确认 —— 文件进了编译列表（`build.bat list` 的文件数）、
真的产出了预期的产物文件、产物内容符合预期。质量闸门实际是「组长在本地跑 `build.bat test`」，
这一点必须如实承认，不能靠 PR 页面的绿灯自我安慰。

### 5.5 判定「不能合入」必须给出可复现的证据，而不是评价

每份审查报告都含：编译错误原文（带 `文件:行:列`）、逐项接口删除清单、
`merge-tree` 零冲突但内容破坏的说明。这样组员能自己复现，也能自己验证整改到位。

最典型的是符号表的两版对比，现在看是一份现成的教学设计：

- **v1**：推倒重写 + 删 17 项公开成员 + 把 `m_ConstInfoTbl` 降为 private →
  `ir.cpp` 出现 8 个编译错误，整个工程编译不过。而提交者只单独编译了 `symbol.cpp`，
  所以自己没发现。
- **v2**：在既有类上增量改造，保留全部接口，作用域栈存扁平下标 → 零删接口、零冲突、
  自带 runner。

两者对照，正好说明「接口即契约」。

### 5.6 区分「能力问题」和「工具问题」

陕海波的语义代码四次失败，对照实验证明代码本身正确、问题在网页编辑器毁文件。
于是方案从「退回重写」改成「整份文件替换 + 教他别用网页上传」。
判错方向会把人推倒重来一遍，代价远大于修 bug 本身。

### 5.7 主动列出「不支持什么」，比含糊说「基本都支持」更经得起追问

`docs/MiniC语法支持清单.md`（465 行）里每一条「不支持」都实际编译验证过，不是照抄文档猜的。
里面几条反直觉的实测结论，答辩时最经得起追问：

- 六个关系运算符**同一优先级**：`a == b < c` 解析成 `(a == b) < c`；
- 顶层语句合法，但声明必须全部写在语句之前；
- 数组长度**只能是整型常量**（`int b[3+5];` 报错）；
- 数组形参语法能过，但语义报 `'a' is not an array`；
- `b = a++` 取**旧值**、`b = ++a` 取**新值**，但 `a += 1` 不支持（`++` `--` 有、复合赋值没有）；
- `1.` 合法、`.5` 不合法；不支持 `0x1F` 与 `1e5`；
- 语义**不检查**下标越界；实参个数与 `return` 类型已在语义阶段检查。

**限定清楚的语言子集，本身就是一个交付物。**

### 5.8 接口冻结 + 变更登记，是多人协作能收敛的前提

`docs/interface.md` 记录 29 项对外接口与 22 条冲突/扩展记录。任何签名改动都要登记并通知相关组 ——
`Q_PARA` 顺序约定如果不写下来，两个组各按自己的理解实现，联调时必然对不上。

### 5.9 任何破坏性操作前先快照

`05_版本快照/` 下有 **15 个带时间戳的快照目录**，以及 `_分支保护配置留档.txt`、
`_删除分支留档.txt`、`_yvechu提交留档/`、`_SHB提交留档_patch3/`、`_GUI删除前备份/`、
`_历史交接文档/`。原则是：任何 merge / reset / 删分支前先快照，出问题可整体回滚。

这条不是形式主义 —— GUI 第一版（Win32 原生）做完后被推翻换成 Electron，旧版已删除
（`4d98c42`），但删除前有备份，所以迭代成本是可控的，也敢在总结里如实写这段弯路。

## 六、不足与改进方向

### 6.1 语言特性层面的限制

| 限制 | 说明 |
|---|---|
| 运算符 | 支持 `++` `--`（前后缀均可）；不支持 `+=` `%` `?:` |
| 语句 | 不支持 `for` / `do-while` / `break` / `continue` / `switch` / `goto` |
| 数据结构 | 不支持多维数组、字符串字面量赋值、逗号表达式、链式赋值 |
| 函数 | 不支持函数原型声明，须先定义后调用 |
| 类型 | 不支持结构体/枚举/typedef；char 已按整型参与算术与关系运算（C 语义的整型提升） |

### 6.2 语义与实现层面的限制

| 限制 | 说明 |
|---|---|
| 顶层声明顺序 | 必须先于语句（LL(1) 固有约束，块内不限） |
| 静态检查缺失 | 不检查数组下标越界（实参个数与 `return` 类型已检查） |
| 条件类型 | `if` 条件是 int 时不报错，只对 `&&` `\|\|` 强制 bool |
| 浮点常量 | `1.` 合法、`.5` 非法 |
| 字符串常量 | 词法识别，语义与代码生成未接 |
| 代码优化 | 已实现**常量折叠**（编译期算出两侧都是常量的算术/关系表达式）；无用代码消除、公共子表达式消除、寄存器分配仍未做 |

### 6.3 工程层面的改进方向

1. **代码优化**：已实现常量折叠（`IRGenerator::FoldBinary`，见 `src/sema/ir.cpp`），
   但整体仍是朴素栈式逐条翻译，没有公共子表达式消除与寄存器分配。
   下一步可以先把折叠扩展到「变量取值已知」的场景，再考虑用图着色做寄存器分配。
2. **错误恢复能力**：语法分析目前用同步集合跳过错误，恢复后可能产生连锁误报。
   可以引入更细的错误产生式。
3. **补 CI**：仓库没有 Actions workflow，分支保护配不了 `required_status_checks`，
   质量闸门只能靠本地跑测试。这是本项目最大的工程缺口，应该优先补上。
4. **个人署名证据链**：12 位成员中有 8 位在 Git 历史里没有独立署名（详见
   `docs/plans/README.md` 第三节）。这个问题在项目收尾时才发现，已经来不及补救；
   正确做法是**项目一开始就让每人用自己的账号提交**。
5. **测试覆盖率**：目前是黑盒行为测试，没有行覆盖率数据。可以接 `gcov` / `llvm-cov`
   补上「哪些代码从未被执行过」这一维度。

### 6.4 收尾时发现、当轮已修的一个断言缺陷

GUI 示例冒烟测试 `gui/test/sample-smoke.js` 原先硬性要求每个示例的运行退出码为 0，
但 `gcd` 示例是 `return t`（gcd(36,24)=12），进程退出码就是 **12** ——
这是 MiniC 返回值语义的正确体现，测试却判定 FAIL。

**这是测试断言写错了，不是编译器错**（输出 12、退出码 12 都符合 C 语义）。
修法：给示例数据加可选字段 `exitCode`，测试按它判定；`gcd` 标注 `exitCode: 12`，
其余示例默认仍要求 0。修完 15 条示例全部通过（含 3 条错误示例）。

留作教训：**测试断言本身也可能是错的**。当测试与语义冲突时，先判断哪一边错了，
不要为了让测试变绿去改被测代码。

### 7.1 协作治理：真正的工作量在这里

多人协作里遇到并处理过的问题：

- 组员**直接往 main 推**；
- **从旧分支切分支**导致覆盖别人的改动；
- **网页版 Add files via upload** 把文件传到仓库根，导致 `build.bat list` 收不到、不参与构建；
- 提交分支是**孤立历史**，开不了 PR。

处置：GitHub 上给 **main 与 dev 都开分支保护**（必须走 PR + 1 次批准 review、
禁强推禁删除，`enforce_admins=false` 保留组长 dev→main 快进能力）；
写《给组员_Git协作流程须知.md》；每个分支合入前用 `git merge-base` 判断能否开 PR。

**必须如实写的一点**：仓库无 CI（Actions workflow = 0），
`mergeable_state=clean` 只表示无文本冲突，不表示能编译。所以「组长本地实测」成了唯一质量闸门。

### 7.2 关于 AI 协作

这个项目的开发过程有 AI 助手参与。如实的定位是：**AI 当执行者，人当判据**。

我做的是三件事：先查真伪（发现两个「能编译但产物是假」的空壳）、
定义验收标准（汇编必须真的链接并运行、输出必须与期望逐行一致）、
逐条核对踩出来的坑是否被真正解决。

AI 出代码的速度很快，但它也会写出「看起来对、跑起来错」的东西。最典型的例子是
`&&` / `||` 的短路：代码里写得「像」短路（有 `Q_JZ` 也有标号），但右操作数在跳转前就被求值了。
这个问题单看代码很难发现，是写了一个「右操作数带 `print`」的用例才暴露的。

**结论：判断有没有实现，看行为不看形状。**

## 九、一句话概括

项目从「两个后端模块是只产固定字符串的空壳」推进到「六段流水线全通、11 套回归全绿、
5 项交付物齐备」，关键不在写代码，而在建立**可验证性**：每个提交都实测编译、跑回归、
比对基线，用证据判定能否合入；每个「全绿」都反向验证过它会不会失败。
期间修掉的典型缺陷包括：构建脚本吞掉退出码（失败也返回 0）、文件放错目录导致 BUILD SUCCESS
的假绿灯、网页编辑器破坏源文件导致的假失败，以及目标代码阶段通过差分测试揪出的实参错序、
返回值语义、`main` 标号重复、IR 类型转换与短路求值等问题。
