## 二、待改进问题（4 项）

### 🔴 问题 1：不识别 UTF-8 BOM（**必修，影响面最大**）

#### 现象

**内容完全相同**的两个文件，仅差一个 BOM，结果天差地别：

| 文件 | 开头字节 | 实测结果 |
|---|---|---|
| `bom_yes.mc` | `EF BB BF`（有 BOM） | ❌ 报 **3 个错误**：`1:1 unexpected character`、`1:2 ...`、`1:3 ...` |
| `bom_no.mc` | `63 68 61`（无 BOM） | ✅ **无词法错误** |

#### 根因

UTF-8 BOM 是 3 个字节 `EF BB BF`，词法器**逐字节扫描时把它们当成 3 个非法字符**（`m_szLexTbl` 里没有对应类别，落到 `default` 分支报"unexpected character"）。

#### 影响（**为什么说这是必修**）

| 场景 | 是否会踩坑 |
|---|---|
| 用 **Windows 记事本** 保存 `.mc` 文件 | ⚠️ **默认带 BOM** → 必踩 |
| 用 **VS Code** 保存 | 可能带（取决于设置） |
| 用 PowerShell `Set-Content -Encoding utf8` | ⚠️ 带 BOM（**本次实测就踩了**） |
| 用 `git` 拉取的组员文件 | 视其编辑器而定 |

**组员很可能用记事本写测试用例，一写就报 3 个莫名其妙的错误，且看不出原因。**

#### 修改建议

在 `CLex::OpenSource()` 读入源文件后，或在 `Run()` 起始处，**跳过 BOM**：

```cpp
// 建议位置：OpenSource() 填充 m_szSource 之后
// 跳过 UTF-8 BOM（EF BB BF）
if (m_szSource.size() >= 3 &&
    static_cast<unsigned char>(m_szSource[0]) == 0xEF &&
    static_cast<unsigned char>(m_szSource[1]) == 0xBB &&
    static_cast<unsigned char>(m_szSource[2]) == 0xBF)
{
    m_szSource.erase(0, 3);   // 或 m_iPos = 3
    // 注意：若用 m_iPos = 3，则列号应从 1 开始计数
}
```

**同时建议**：

- 项目 `.gitattributes` 或 `.editorconfig` 里约定 **`.mc` 文件统一用 UTF-8 无 BOM**
- 文档中注明此约定

#### 验收标准

```
带 BOM 的 .mc 文件 → 不再出现 "unexpected character" 错误
带与不带 BOM 的同一文件 → token 输出完全一致
```

### 🟡 问题 2：多字符字符常量报错后**仍产出 token**（导致同一错误报两遍）

#### 现象

**输入**（第 2 行）：
```c
a = 'ab';
```
**字符 `'` 的实际位置**：第 2 行 **第 5 列**

**实测报错**：
```
2:5: multi-character char literal
```

#### 分析

列号 `2:5` **是准确的**（正确指向 `'ab'` 的开头），这点没问题。

**真正的问题是**：报错后**该多字符常量仍被当作一个 `CHAR_CONST` token 产出**：

```
2:5  CHAR_CONST  'ab'
```

**这意味着**：词法阶段报错了，**但仍把它交给语法阶段**，语法阶段又报一次错：

```
2:5: expected number, identifier or '(' , but found ''ab'' (CHAR_CONST)
```

#### 影响

**同一个错误被报两遍**（词法一次、语法一次），错误信息重复，干扰定位。

#### 修改建议

**二选一**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A** | 多字符常量报错后，**只取首字符**产出 `CHAR_CONST`（如 `'a'`），**不报错** | 与 C 语义不同，但宽松 |
| **B（推荐）** | 报错后**跳过整个字面量**，**不产出 token**，让语法阶段自然发现缺失 | 错误只报一次，干净 |

> C 语言实际行为：`'ab'` 是 **implementation-defined**（多数编译器接受并取某字节）。既然本项目要求严格，建议按 **B** 处理。

#### 验收标准

```
输入 a = 'ab';
期望：词法报 1 个错（multi-character char literal），且不再产出 CHAR_CONST token
      语法阶段不再重复报同一个错
```

### 🟡 问题 3：字符串常量 `STRING` 的**定位未明确**

#### 现象

**实测**：
```c
print("hello");
```
词法输出：
```
1:4  PRINT     print
1:9  LPAREN    (
1:10 STRING    "hello"     ← 词法能识别
1:17 RPAREN    )
```
**但**：文法中**没有字符串终结符**，语法阶段**无产生式可匹配**。

#### 分析

这是**设计决策问题，不是 bug**。设计文档 §15.1 给了三个选项：

| 选项 | 内容 | 状态 |
|---|---|---|
| **A** | 保留词法能力，**不入文法**（默认） | 当前实现即此 |
| B | 删除 `TOKEN_STRING` 与 `ScanString()` | 未选 |
| C | 扩展文法支持字符串字面量 | 未选（代价：整套表格需重生成） |

#### 当前问题

**方案 A 虽被默认采用，但没有在代码或文档中明确"不支持"这一事实**，导致：
- 组员写 `print("abc")` 会困惑为什么报错
- 词法保留了能力，却"无人使用"

#### 修改建议

**保持实现不变**（按方案 A），但**补两处说明**：

1. **`token.h` 中 `TOKEN_STRING` 加注释**：
   ```cpp
   TOKEN_STRING,   // 词法扩展：挑战版文法不支持字符串字面量，仅作词法能力保留
   ```
2. **《词法模块改造任务书》或 README 中注明**：
   > `print` 仅接受表达式（数值/布尔/字符/变量），**不支持字符串字面量**。

#### 或

若组里决定**不需要**字符串能力，则**明确删除** `TOKEN_STRING` + `ScanString()`，并同步修改 `tests/lex_test.mc`（该用例含字符串）。

### 🟢 问题 4：**5 个测试用例缺配套期望输出**（不阻塞功能，但影响回归）

#### 现象

任务书 §7.1 要求为新用例补 `*.token.txt` 期望产物，用于回归断言。**实测检查**：

| 用例文件 | 期望输出 `*.token.txt` |
|---|---|

| `lex_op_edge.mc` | ❌ **缺** |
| `bad_char.mc` | ❌ **缺** |
| `bad_op.mc` | ❌ **缺** |
| （对比）`test.mc` | ✅ 有 `test.token.txt` |

#### 影响

**无法做自动化回归**——后续任何人改动词法器，都没有基线可比对，容易悄悄改坏。

#### 修改建议

1. 为每个新用例生成一次期望输出：
   ```bash
   ./build/minic.exe tests/lex_challenge.mc --dump-tokens
   # 产出 tests/lex_challenge.token.txt
   ```
2. **人工核对**输出正确后，**提交进仓库**作为基线
3. 后续可加一个简单的回归脚本比对

**注意**：`bad_char.mc` / `bad_op.mc` 是**错误用例**，期望输出应包括**错误信息**（可能需要重定向 stderr 保存）。

**同时建议**：

## 五、建议的修改顺序

```
① 先修 BOM 识别（P0）          ← 影响最大，独立改动，风险低
       ↓
② 补 STRING 注释（P1，0.2h）    ← 顺便做掉
       ↓
③ 多字符常量恢复策略（P1）      ← 需先确认选 A 还是 B
       ↓
④ 生成并提交 5 个期望输出（P2）  ← 需在 ①②③ 完成后做，否则基线会变
       ↓
⑤ 加 .editorconfig（P2）
```

> **注意顺序**：**第 ④ 步必须最后做**——因为前面几项修改会改变 token 输出，
> 若先提交基线再改代码，基线就失效了。
