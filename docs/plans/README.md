但在 **Git 历史里没有可见贡献**。两者不一致这件事本身，比"文档写全了"更值得记录。

### 3.3 三处需要如实说明的落地情况

1. **词法组共用账号**：`lexer-dev` 是两人协商共用的提交身份。这不是"凑贡献"，
   而是两人在同一 worktree 上交替改代码、共同提交的产物。文档里按「侧重面」分工
   （刘鑫泽侧重实现、张吕柘冰侧重形式化定义与基线）是为了让人看懂各自做了什么，
   但 **Git 层面无法据此区分两人的贡献比例**。

2. **语义模块由组长代实现**：《04_语义分析模块_陆禹辰_陕海波_于霄.docx》第三节原文写明
   「本次 `semantic.*` 由组长代实现，原稿来自陕海波的方案」，
   并要求「把实际分工写进 `docs/plans/` 的个人计划，并在小组分工表里据实登记（不要写「未开工」）」。
   三份语义文档因此按「各自负责的节点行为」划分（陆禹辰：分派与类型推导；陕海波：遍历骨架与
   类型推导统一出口；于霄：声明登记与作用域进出），并明确标注了代实现的边界。

3. **目标代码模块由组长代为落地**（见 `2416050323_王逸凡_目标代码.md` 第五节）。
   项目进入收尾阶段时中间代码与目标代码是唯一关键路径，需要一次性拉通；
   王逸凡本轮承担接口对齐与联调约定（`docs/interface.md` 第 14 条）。这一情况写在该文档里，不藏。

### 3.4 建议的补救动作（交给组长决定）

- 让有 GitHub 账号的成员**各自补一次真实提交**（哪怕只是修正自己负责的注释、补一个用例），
  个人过程分的证据链才立得住。
- 小组分工表（项目书表 3）已按本目录回填到 [docs/小组分工表.md](../小组分工表.md)，
  **「核心任务职责」列写的是实际做的事**，不写「未开工」，也不夸大。
- 若课程方按 Git 提交量算个人过程分，8 位零提交的成员需要提前向老师说明原因，
  而不是等验收现场被问出来。
