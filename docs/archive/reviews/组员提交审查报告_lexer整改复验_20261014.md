## 三、本轮新发现（不影响合入）

### 🟡 新发现 1：5 个词法基线里 4 个带 UTF-8 BOM，1 个不带

| 文件 | 字节 | 首 3 字节 | BOM |
|---|---|---|---|
| `tests/bad_char.token.txt` | 182 | `EF BB BF` | 有 |
| `tests/bad_op.token.txt` | 164 | `EF BB BF` | 有 |
| `tests/lex_challenge.token.txt` | 1525 | `EF BB BF` | 有 |
| `tests/lex_op_edge.token.txt` | 593 | `EF BB BF` | 有 |
| `tests/lex_char.token.txt` | 509 | `32 3A 31`（`2:1`） | **无** |

**成因**：组员用 PowerShell 重定向生成基线，PS 7 的 `>` 默认写 UTF-8 **带 BOM**（这个 BOM 是 `Out-File` 加的，不是程序的）。

**为什么不是阻塞项**（已实测）：项目既有的比对函数 `Read-Text` 用 `[System.IO.File]::ReadAllText()`，**.NET 会自动剥离 BOM**。实测写入带 BOM 的文件再 `ReadAllText`，首字符是 `U+0048`（`H`）而非 `U+FEFF`。所以按 `Normalize`+`Read-Text` 的常规方式比对，**BOM 不会导致 FAIL**。

**但仍建议统一**，理由有三：
1. 5 个基线应保持同一种编码，现在 4 有 1 无，属不一致；
2. 仓库 `origin/dev` 上**带 BOM 的文本文件数为 0**（全仓库扫描确认），这 4 个是唯一例外，与项目约定相悖；
3. 若将来有人做字节级/哈希级比对，BOM 会立刻造成假失败。

**修法**（一行，与项目既有 `Write-Golden` 完全一致）：

```powershell
# tests/run_parser_tests.ps1:109-112 已有的写法，直接沿用
$utf8 = New-Object System.Text.UTF8Encoding($false)   # $false = 不写 BOM
foreach ($f in @('bad_char','bad_op','lex_challenge','lex_op_edge')) {
    $p = "tests\$f.token.txt"
    $t = [System.IO.File]::ReadAllText($p)            # 读入时 .NET 自动剥 BOM
    [System.IO.File]::WriteAllText($p, $t, $utf8)     # 写回时不带 BOM
}
```
